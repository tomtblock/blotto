## 1. System inventory and trust map

### 1.1 What this system is, in the words of someone who just read the code

An Anchor program on Solana devnet runs a sealed-allocation tournament and holds every lamport in
two kinds of zero-data, System-owned account: one platform treasury PDA that receives 100% of every
entry payment, and one prize-vault PDA per pool that is pre-loaded with a fixed pot before a single
entry is sold. A browser encrypts seven battle allocations to a per-pool X25519 key, posts the
ciphertext to a service, asks that same service for an Ed25519-signed entry packet, and then sends
one transaction that carries the packet, moves the entry price to the treasury, draws a cosmetic
class, mints a frozen pass and records a 32-byte hash of the allocations. The program never sees an
allocation. A daemon polls the chain every fifteen seconds, seals pools at their deadline, exports
each pool's secret from custody, decrypts and verifies every stored ciphertext against its on-chain
hash, scores the field all-against-all in integer half-points, publishes the whole reveal to Irys,
screens winners against sanctions lists, commits a Merkle root and pays. An indexer ingests the
program's events through an authenticated webhook into an append-only ledger plus nine derived
tables, and serves an unauthenticated public read API the app reads from. A fourth service accepts
wallet-signed review decisions and appeals.

The README describes the same system. The gap between this paragraph and the README is not the
problem; the gap between both of them and the running code is (§2).

## 2. Executive verdict

**DO NOT SHIP.**

Three things matter, in this order.

**Settlement cannot work, and two separate one-line defects prove it independently.** The browser
stores each player's sealed allocation under one key and the crank reads it back under another, so
every entry resolves to "ciphertext missing", every player is scored all losses, and the fixed pot
divides equally across the field — after the pool secret has already been published on chain, which
cannot be undone. Separately, the settlement client sends the Config account read-only on the one
instruction that pays winners, while the program declares it mutable, so every payment batch reverts
before the handler runs. Either defect alone ends the first real pool.

**An unauthenticated endpoint decides who wins.** Anyone can overwrite any named entrant's sealed
allocation with 175 random bytes: no signature, no packet, no ownership proof, no pool-state check.
Today the key defect masks it. The moment that is fixed, it becomes a way to take the prize pool.

**All three survived for one structural reason.** There are 121 test files and not one crosses a
process boundary. The test that appears to cover the ciphertext handoff reads it back through the
producer's own key transform; the twenty-pool rehearsal writes to the store directly and skips the
HTTP route; the read-API tests answer their own SQL from a canned stub; the only end-to-end harness
is invoked by no workflow. A green suite here is evidence about units, not about the system.

One thing is genuinely good: the on-chain money model is disciplined and, on its own terms, correct.

### CRITICAL

#### B-01 · Sealed allocations are written under one key and read under another, so no pool can ever be scored

**Locations**
- `backend/packet/src/server.ts:205` — the write, `put(poolKey(b.pool), …)`
- `backend/packet/src/server.ts:212-217` — `poolKey`, a 62-bit polynomial hash of the pool address
- `backend/packet/src/main.ts:146` and `backend/reveal/src/main.ts:262` — both wire a bare `PgCiphertextStore`
- `backend/reveal/src/ranking.ts:83` — the read, `ciphertexts.get(poolId, e.player)` with the on-chain numeric id
- `backend/indexer/src/read-api.ts:420` — a third consumer, `JOIN sealed_entries s ON s.pool_id = p.id`
- `backend/_shared/migrations/0002_sealed_entries.sql:4-10` — `pool_id NUMERIC`, no foreign key, so the wrong key inserts silently

**What's wrong.** The browser posts the pool's PDA address as `pool`; the route's own base58 check
makes it impossible for a numeric id to arrive. The handler converts that address with `poolKey`, a
polynomial hash producing a 62-bit number, and writes it into `sealed_entries.pool_id`. Every reader
uses the pool's on-chain numeric id instead — a small integer. The comment above the write says a
PDA-to-id resolver arrives "at deployment"; the deployment file three directories away wires the
store straight through with no resolver.

**How it is hit.** No attacker. A pool fills, seals, and the crank runs. It reveals the pool secret
on chain first — irreversible — and only then looks up each entry's ciphertext. No row can match, so
every entry takes the `missing_ciphertext` branch and is scored all losses. Nothing aborts on a
field that is entirely missing: every seat then ties on rank 1, conservation still passes, and the
crank commits and pays a payout list that divides the entire fixed pot equally among all 52 to 64
entrants.

**Blast radius.** Every pool, every player, from the first one onward. The pot is paid out wrongly
and irreversibly; the published bundle records the whole field as unscored; the results pages serve
nothing because the read API shares the defect; and the operator is left owing every entrant their
entry price. This is the product's core journey completing with the wrong answer.

**Fix sketch.** Resolve the pool address to its on-chain numeric id in
`backend/packet/src/server.ts` before writing — the `pools` table already holds that mapping and the
read API performs the same lookup — and reject the write when the pool is unknown. Delete `poolKey`
rather than leaving a second key space in the codebase. The durable half is a test that posts
through the HTTP handler and reads back through the crank's own path.

**Confidence: High.** Confirmed independently by three of the audit's lane finders, by the
verification pass, and by hand.

#### B-02 · `POST /ciphertexts` is unauthenticated and last-write-wins, so anyone can overwrite any entrant's sealed allocation

**Locations**
- `backend/packet/src/server.ts:186-207` — the handler: base58 shape and a 175-byte length, nothing else
- `backend/sealing/src/store.ts:70-78` — `ON CONFLICT (pool_id, player) DO UPDATE SET ciphertext = EXCLUDED.ciphertext`
- `backend/reveal/src/ranking.ts:92-116` — a failed decryption or a hash mismatch is scored all losses
- `backend/reveal/src/missing.ts:50-58` — every other player is credited a full win against an all-losses entry

**What's wrong.** The route validates that `pool` and `player` look like addresses and that the body
decodes to exactly 175 bytes. There is no wallet signature, no entry packet, no proof the caller
controls `player`, no check that the pool exists or is still open, and no check that the player has
an on-chain entry. The store's write is an unconditional upsert. The sibling routes `/attestation`
and `/notify` both verify a wallet signature, so this is a specific omission rather than a
service-wide gap.

**How it is hit.** Enter one pool legitimately. Harvest every `(pool, player)` pair from the public
entry events or the indexer's own entries feed. For each rival, send one unauthenticated request
with 175 random bytes. Wait for the pool to seal so victims cannot repair. At settlement every
overwritten rival fails its hash check and is scored all losses, you win every battle against each
of them, and the vault pays you the whole prize pool.

**Blast radius.** The entire pot of any pool, taken by an HTTP client with no wallet and no on-chain
footprint beyond one ordinary entry. Also a targeted way to destroy any named entrant's paid entry,
and an unbounded write into the database the indexer, daemon and read API all share.

**Fix sketch.** Require proof of control of `player` on this route: an Ed25519 signature by that
wallet over a canonical message binding the pool, the player and a hash of the ciphertext, verified
exactly as `backend/packet/src/attestations.ts:102` already does for the clickwrap. Separately,
refuse a write whose pool is unknown or no longer open, and refuse to overwrite a row once the pool
has sealed.

**Confidence: High.**

#### B-03 · One lamport sent to a prize vault blocks that pool's payout and its refund fork

**Locations**
- `programs/blotto_cup/src/instructions/open_pool.rs:154-160` — the vault is funded with exactly `pot_lamports`
- `programs/blotto_cup/src/vault.rs:60-81` — `vault_debit` transfers a computed amount, never the balance
- `programs/blotto_cup/src/instructions/pay_prizes.rs:146-153` — pays the committed amount
- `programs/blotto_cup/src/instructions/refund.rs:83-96` — returns exactly the pot
- `docs/internal-review.md:42-49` — the project's own note accepting this risk as harmless

**What's wrong.** The prize vault is a zero-data, System-owned account, and the design drains it to
exactly zero: the refund path's own comment says "the vault holds exactly the pot; debiting it all
reaps the vault", and every integration test asserts the vault reads zero afterwards. The Solana
runtime refuses any transaction whose post-state moves a writable account from rent-exempt to
rent-paying. A zero-data account is rent-exempt only at or above 890,880 lamports, and zero is the
only other permitted end state. A vault left holding anything between one and 890,879 lamports after
a debit therefore fails the whole transaction.

**How it is hit.** After a pool opens, send its vault — an address anyone can derive from the public
pool id — one lamport. That transfer succeeds, because the vault is already rent-exempt. Every exit
debits a fixed computed amount, so the final debit now leaves one lamport behind and the runtime
rejects the transaction with an insufficient-funds-for-rent error. With a single paid place, the
winner's payment *is* that final debit. The refund fork breaks identically, because it returns
exactly the pot.

**Blast radius.** Per attacked pool: the pot is unpayable, the entrants are unpaid, and because the
tier's slot is freed only by `pay_prizes` or the two refund paths, no further pool can open in that
tier. Cost to the attacker is one lamport plus a transaction fee, and pool addresses are derivable
in advance, so many pools can be poisoned at once. There is a rescue — top the vault up so the
residue lands at or above the rent-exempt minimum — but it appears in no code, test, script or
runbook, and diagnosing it requires knowing a runtime rule the program never mentions.

**Why it survived.** `docs/internal-review.md:42-49` records this exact scenario, considered and
accepted: "Nothing in the program reads those balances to make decisions … so a donation strands
harmlessly. No action." The reasoning is correct about the program and wrong about the runtime. The
program never reads the balance; the runtime does. The integration suite cannot see it either,
because the in-process test validator does not model the rent-state transition check.

**Fix sketch.** Make `vault_debit` in `programs/blotto_cup/src/vault.rs` rent-aware: when the
post-balance would be non-zero and below the rent-exempt minimum, sweep the residue into the same
transfer so the vault lands at exactly zero — gated on the final debit for the batched payment path.
The alternative is to fund every vault with the rent-exempt minimum on top of the pot at
`open_pool` and to leave that minimum behind on every exit. Either way this is a program change and
needs the redeploy sequence.

**Confidence: High.**

#### A-01 · `pay_prizes` cannot be called by the production client, so no pool can ever be paid

This is the dead-code lane's most valuable category: code that is unreachable *because a wiring
mistake made it unreachable*.

**Locations**
- `backend/reveal/src/chain-web3.ts:497` — `{ pubkey: this.configPda(), isSigner: false, isWritable: false }`
- `programs/blotto_cup/src/instructions/pay_prizes.rs:56-62` — `#[account(mut, seeds = [CONFIG_SEED], bump = config.bump, has_one = settlement_signer)]`
- `programs/blotto_cup/src/instructions/pay_prizes.rs:180-193` — the handler writes Config
- `backend/reveal/src/crank.ts:293` — the only caller

**What's wrong.** The program declares the Config account mutable on `pay_prizes` and the handler
writes it, releasing the pot from the treasury's reserved figure and freeing the tier slot. The
production settlement client builds the instruction with Config marked read-only. Anchor evaluates
the `mut` constraint while assembling accounts, before the handler runs, so the transaction reverts
on every batch and every retry — not only on the final one.

Every other instruction the same client builds gets this right. Checked one by one: `open_pool`,
`seal_at_deadline`, `trigger_refund` and `refund` all mark Config writable and all declare it
mutable; `reveal_pool_secret`, `commit_results`, `release_escrow`, `forfeit_escrow`,
`pay_next_place`, the flag pair and the sanctions pair all send it read-only and none declares it
mutable. `pay_prizes` is the single mismatch, on the single instruction that pays players.

**How it is hit.** Run any pool to settlement on the deployed stack. Reveal and commit succeed; the
crank reaches the payment step and every batch reverts deterministically. The pool is stuck in
`Scored` for ever: nobody is paid, the paid mask stays empty so `Paid` is never reached, the tier
slot is never freed so no successor pool can open in that tier, and the pot stays counted against
the treasury's reserve.

**Why it survived.** The integration suite drives the compiled program through a hand-built
byte-level client of its own, so it constructs correct account metadata and tests the program rather
than the client. The daily drift detector, which exists precisely to catch a wire-contract
mismatch, simulates 19 of the program's 32 instructions — the admin surface, `migrate_config`,
`pay_next_place`, the sanctions pair and a canary — and none of the money-moving instructions the
daemon actually sends. It then prints "every instruction's wire contract matches this branch"
(`scripts/check-deployed.ts:550-551`).

**Fix sketch.** Mark the Config account writable in `Web3Chain.payPrizes`. The durable half is a
test that, for each instruction, compares the writable set the client emits against the `mut` set in
the corresponding accounts struct — nothing compares them today. Extending the drift detector to
cover the settlement instructions closes the same gap from the other side.

**Confidence: High.**

### HIGH

#### B-04 · The paid geo vendor's daily quota is a single point of failure for all entry, is consumed by unauthenticated page views, and its exhaustion refuses every entry with no alert

**Locations**
- `backend/packet/src/server.ts:L115-L118`
- `backend/packet/src/geo-cache.ts:L23-L26`
- `backend/packet/src/geo-iplocate.ts:L40-L51`
- `backend/packet/src/geo-iplocate.ts:L120`

**What's wrong.** GET /geo is unauthenticated and takes no body; every request for a previously unseen client IP
costs one IPLocate lookup (CachingGeoLookup keys on the IP itself with a 15-minute TTL, geo-
cache.ts:60-79). The app fires it from a useEffect on every mount of /play (play-
client.tsx:202), so every visitor — entrant, bot or crawler — spends quota. The service's own
comments state the budget: geo-cache.ts:23-25 says "two lookups per entrant across 64 entrants
is 128 per pool against a 1,000/day cap over a finite, non-renewing credit balance", and
main.ts:70-73 repeats it.

**How it is hit.** Point ~1,000 distinct source addresses (a cheap residential-proxy pool) at GET https://<packet-
host>/geo once each — no body, no wallet, no signature — and each unseen IP misses the 15-minute
per-IP cache and spends one IPLocate credit. Once the daily cap is reached IPLocate answers 429,
which geo-iplocate.ts:120 deliberately never retries, so geoVerdict returns false and
issuePacket's catch returns the generic rejection for every caller. Entry is then impossible for
every real player until the cap resets, nothing pages anyone (the only signal is a console
line), and repeating it across the fill deadline pushes pools under MIN_SEATS into refund; the
same outcome arrives accidentally from ~1,000 launch-day visitors to /play.

**Blast radius.** Total, silent denial of the one journey that takes money, for a whole quota day, triggerable by
an unauthenticated attacker or by ordinary launch-day traffic. Pools that cannot fill past their
deadline go to the refund fork.

**Fix sketch.** Three changes in backend/packet/src: raise the geo path above a single hard-capped credit
balance (a paid tier or a second vendor behind the same GeoLookup seam, composed the way
backend/sanctions/src/composite.ts composes sources); alert on GeoQuotaError/GeoAuthError
specifically rather than only console.error in service.ts:177-181, wiring the shared monitor
into main.ts as the other services do;

**Confidence: High.** All six citations check out: GET /geo is unauthenticated (server.ts:115-118), CachingGeoLookup
keys on the raw IP with a 15-minute TTL and never caches failures (geo-cache.ts:60-79), the app

## 4. Lane A — Dead code

35 findings: 1 CRITICAL, 12 MEDIUM, 22 LOW. Classification of the dead-code candidates:
13 SAFE-DELETE, 9 UNREACHABLE-BUT-LOAD-BEARING, 7 SUSPECTED-BUG.

The file-level picture is unusually clean. A full import graph over `app/src` with the alias
resolved found zero orphan files, zero unresolved imports and no file named for a superseded
version. An automated sweep over all 423 exported symbols in `backend/*/src` found almost nothing
unused that is not a deliberate in-memory test double. The on-chain program is clean too: every
instruction has a real caller, every event is emitted, and no account field is written without being
read somewhere.

What the lane did find is the more valuable category. **Seven whole mechanisms are wired to nothing
while their own documentation says they are live.** Each is detailed in §3; the identifiers below
point into that list.

- **A-01 (CRITICAL)** — `pay_prizes` is unreachable through the production client, because the
  client sends one account with the wrong mutability. Detailed in §3.
- **A-08** — the published-bundle archive is never populated: the announce variable is staged
  nowhere, and the backfill command that was meant to cover for it is scheduled by nothing. The
  consequence reaches players: rank labels and the results link never render, and every profile rank
  is null.
- **A-05** — the email opt-in is collected, wallet-signed and stored, and no dispatch path exists
  anywhere in the tree, while the interface states that an email will be sent.
- **A-06** — the cluster and RPC "build-time gate" never runs in the deployment path; it is reached
  only from a unit test.
- **A-07** — a production deploy missing the indexer URL silently serves a fabricated fixture
  catalogue, with a working entry control on it.
- **A-10** — the email notification table is written and never read: the opt-in is stored, the
  interface promises a message, and no dispatcher exists.
- **E-01** — the metrics sink, the metrics route and the alert channel have no caller in any shipped
  configuration, and only one of the four services builds a monitor at all.
- **A-04** — the review decision log destroys the signed timestamp on read-back, so no published
  decision verifies against its own signature.

The remaining LOW findings are genuine dead code with no path to harm: an orphan package, a dead
adapter arm, a superseded geometry module, eleven unreferenced copy keys, a dead server-side auth
subsystem carried from a predecessor repository that still forces a secret onto the deploy

are safe to remove in a separate sweep.

Two things classified UNREACHABLE-BUT-LOAD-BEARING and deliberately **not** recommended for
deletion: the migration instruction, which is unreachable on a fresh deployment but is exactly what
the pending devnet upgrade needs, and two error variants that are never returned but hold their
numbering for clients that check error codes.

## 5. Lane B — Vulnerabilities

55 findings: 3 CRITICAL, 6 HIGH, 31 MEDIUM, 15 LOW. Boundary by boundary, from the trust map in §1.3.

**The on-chain program is the strongest part of the system.** Every one of the 16 admin-surface
instructions has a signer check and a `has_one` constraint, verified individually. PDA seeds and
bumps are validated everywhere; account substitution is closed by seed derivation plus explicit
pool-and-index binding on every entry read. Arithmetic is integer-only with overflow checks on in
release. The entry packet is read from the instructions sysvar rather than from anything the caller
asserts, its self-referential offsets are validated so a packet cannot be pointed at bytes the
native program did not verify together, and it is bound to wallet, pool and a sixty-second window —
so a packet issued for one wallet is unusable by another, and replay by the same wallet is closed
structurally by the entry account's seeds. Double payment is closed on both sides. The four
documented vault exits really are the only ones, confirmed by exhaustive grep.

The one CRITICAL against the program is B-03, and it is not a logic error: it is a runtime rule the
program does not account for.

**The packet service is where the damage concentrates.** Its compliance logic is disciplined —
territory decisions fail closed at every edge, the header-spoofing bypass of an earlier incident is
genuinely fixed and regression-tested, the development signer cannot be selected without an explicit
opt-in, and neither the geo nor the sanctions cache ever caches a failure. But one route on that
service has no authentication and the wrong key, and that route decides the outcome of every pool
(B-01, B-02).

**The indexer is clean on injection and weak on limits.** All 34 query call sites were inspected:
every user-controlled value is a bind parameter, the only interpolated identifiers come from an
internal operation list behind a strict pattern check, the filters are allowlisted before they reach
SQL, and there is no dynamic ordering or limit clause. The damage is elsewhere — two public
endpoints materialise unbounded result sets, the webhook buffers before it authenticates, and the
"verified archive" serves three fields the Merkle root does not cover (B-04 to B-09).

**The review service's signature scheme is sound.** The canonical message covers every field that
matters, so no unsigned field can alter a decision in transit, and the appeal message's distinct
header makes cross-type reuse impossible. Its failures are at the seams: a signature replayable for
five minutes with the replay material published on an unauthenticated route, a decision log that
destroys the signed timestamp on read-back so no published decision verifies against its own
signature, and authentication used as authorization — any single registry member can act on any
entry in any pool.

**The browser app produced no vulnerability findings at all**, across 57 files read. No server
routes beyond an image handler, no cookies or sessions, no secret reachable from the bundle, and no
cross-site-scripting sink anywhere: the dangerous rendering hooks, `eval` and cross-window messaging
all return zero hits. The transaction seam simulates before it asks for a signature, the wallet
signs before any local co-signer, and the error map was verified correct against the program's own
error enum. This is a real result, not an absence of effort.

**Supply chain and logging** split the other way from expectation: the lanes that hold no
credentials pin every action by commit and install only from committed lockfiles, while the one
workflow that binds the settlement keypair, the custody private key and the infrastructure token
takes a third-party action from a mutable branch and declares no permissions block. No credential is
committed anywhere in the tree. The logging gap is the inverse kind: a sanctions match at entry is
recorded with a truncated address and no wallet, in no store; the unauthenticated ciphertext write
logs nothing at all, so an overwrite of another player's entry would be undetectable after the fact.

## 6. Lane C — Dead ends

36 findings: 4 HIGH, 23 MEDIUM, 9 LOW.

**One fact dominates the lane.** Every non-terminal on-chain state — sealed, scored, refunding,
escrowed, forfeited — has exactly one exit, and that exit is the settlement daemon. The admin
tooling has no command that can seal, reveal, commit, pay, refund, release or free a tier slot. The
daemon is also the one service the scheduled health probe does not cover. So the whole of settlement
is that one process or nothing, and nothing watches it.

Worse, the states are not symmetric. Once a pool seals, the refund path refuses it, so a pool that
cannot be settled cannot be unwound either. Three of the four HIGH findings in this lane are
versions of that shape: an upload failure before the payment step strands a sealed pool and its
whole tier (C-01); a screening vendor that merely fails to answer converts into a permanent on-chain
hold with no automated release (C-02); and in the browser, a hung sign-in and an unreachable review
service each render as nothing at all, with no timeout, no explanation and no control (C-03, C-04).

**The adapter guards are mostly excellent.** The development entry signer, the sanctions stub, the
randomness stub and the browser test signer each require an explicit opt-in, and the test signer is
additionally eliminated at build time and proven absent by a two-sided CI gate. Two exceptions: the
geo stub selects on a single variable with no opt-in, and the app falls back to fabricated fixture
tournaments when the indexer URL is unset — contradicting the fixture module's own claim that it
cannot reach production.

**Vendor outages** were traced one by one. Most fail closed correctly. The ones that do not fail
*well*: a stalled response body has no timeout on any vendor call except one that was explicitly
fixed after an incident; a sanctions source past its staleness limit throws and is announced by
nothing but a console line; and an unfunded upload wallet is discovered at settlement rather than at
startup.

## 8. Lane E — Config, environment and deploy

22 findings: 10 MEDIUM, 12 LOW. No CRITICAL or HIGH of its own; the configuration defects that matter
are counted against the mechanisms they disable (A-08, C-02).

**What the deploy asserts.** The backend deployment is hardened at the infrastructure layer and
every guard has a dated incident behind it: the platform token is probed with a real call before
anything is built, every credential is classified up front and a missing one stops the run by name,
the development signer seed and the geo stub are actively unset when the real credential is staged,
applications and addresses are asserted rather than assumed, and machines are asserted started
because a deploy updates a stopped machine without starting it.

**What it does not assert.** It runs no test, no typecheck and no lint. It is dispatch-only with no
dependency on a green build and nothing constraining the selected revision. A partial deploy is
possible and likely: one job ships four services in sequence with cancel-in-progress on, so a second
click abandons the first halfway and leaves the fleet on mixed builds, and nothing afterwards
compares what is running against what was meant to run. If a credential is missing the workflow does
not fail — it silently drops the settlement daemon and the review service from the deploy and
finishes green.

**Migrations** run forward-only at indexer boot, one transaction each, with no advisory lock and no

## 9. Lane F — Data integrity

19 findings: 3 HIGH, 5 MEDIUM, 11 LOW.

**The money arithmetic is right, and that matters more than the finding count suggests.** Prize
splitting is integer-only end to end; the Rust and TypeScript implementations of the split rule
agree; the TypeScript path asserts conservation rather than assuming it; every lamport is a bigint;
every currency column is numeric and bound as a decimal string. No float exists on any scoring or
payout path. The five-stats-summing-to-100 rule is enforced by the program, by the payload encoder
and by the client.

**Drift risk is lower than expected**, and for a good structural reason: the browser imports the
backend's scoring, ranking and Merkle modules directly through path aliases, so the code a player
runs to verify a result is literally the code the crank ran to produce it. There is no second
implementation to diverge. The three places where two implementations do exist — the prize split,
the class-counter table and the entry packet encoding — are each pinned to shared generated
fixtures, except the class-counter table, whose header claims an assertion that does not exist in
any of its three copies.

**The three HIGH findings are all absences rather than errors, and they compound.** Settlement
commits and pays with no sanity check on how many ciphertexts were actually readable (F-01): the
all-losses list is computed, written into the published bundle, and consulted by no decision, so a
pool in which every entry failed to decrypt settles exactly like a pool in which none did. The
sealed entries that would be missing in that scenario exist in exactly one place — one Postgres
table, with the chain holding only their hashes — and there is no backup posture, no restore
procedure and no rehearsal anywhere in the documents, the deployment files or the workflows (F-02).
And the check a player is told to run to catch a wrong settlement does not close the loop either:
the verify page confirms that every entrant *in the published bundle* matches the chain, and never
that every entrant *on the chain* appears in the bundle (F-03). Dropping the highest-indexed
entrants from a published bundle therefore passes all six of its checks, and the program does not
close the gap because it validates only that each committed seat index is below the entrant count.

The MEDIUM findings are invariants assumed but not enforced at the layer that would catch a
mistake: several application-level uniqueness rules have no database constraint behind them, and the
settlement client decodes two account types from about 45 hardcoded byte offsets with no length
check — while the neighbouring decoder for a third type does guard, and a cross-language pin exists
for a fourth. The header of that pin records that this exact defect class has already fired once.

## 11. Lane H — Hunches, and how to confirm them

Twelve things this audit suspects and could not prove in this pass. Each carries the command or
experiment that would settle it. They are not findings and should not be treated as such.

1. **The platform treasury has the same rent-exemption trap as the prize vault (B-03).** It is also a
   zero-data account, and the refund path debits exactly the entry price per entry, so a treasury
   standing at a small residue above the withdrawal floor would fail its last refunds. *Confirm:*
   add a LiteSVM case that sets the treasury policy floor to zero, withdraws down to the refundable
   sum plus 100 lamports, then lands all 52 refunds and asserts the last one succeeds.

2. **The in-process test validator may not model the rent-state transition check at all**, which
   would mean a regression test for B-03 passes locally while the real chain still rejects. *Confirm:*
   in an existing passing lifecycle case, airdrop 1 lamport to the vault before the final payment and
   re-run. If it stays green, the harness cannot see this class of defect and the fix must be
   validated against a real validator.

3. **The devnet database may already contain rows under the wrong key**, which would confirm B-01
   against live data rather than by reading. *Confirm:*
   `SELECT pool_id, count(*) FROM sealed_entries GROUP BY 1 LIMIT 20;` alongside
   `SELECT id, pool FROM pools ORDER BY id LIMIT 20;` — the two ranges do not overlap, so one query
   settles it.

4. **The live services may not have the hygiene switches set**, in which case rate limiting, CORS
   and security headers are all off in production. The deploy stages them, but that workflow is
   manual and no committed deployment file sets them, so a machine last deployed by hand would not
   have them. *Confirm:* list the secrets on the running applications and grep for the three names.

5. **Two daemon instances may be alive at once** during a deployment overlap or a health-check
   restart, both against the same database. Correctness does not depend on mutual exclusion — the
   on-chain write-once flags close the dangerous races — but the cost and the log noise would be
   real. *Confirm:* list the machines for the daemon application during a deploy.

6. **Two migration runners may race on a cold start**, since each migration runs in its own
   transaction with no advisory lock. The loser hits a conflict and throws. *Confirm:* start two
   indexer processes simultaneously against an empty database.

7. **The browser bundle may be reaching Node built-ins** through the sealing package's barrel export,
   which re-exports a custody module that imports the crypto module. *Confirm:* build the app and
   grep the client chunks for the built-in module name.

8. **The mainnet launch will reproduce the deployment-hijack window** described in A-02, because the
   deploy script ends at the program deploy and the initialisation is a separate multisig proposal.
   *Confirm:* read whether any mainnet runbook lands initialisation in the same transaction as the
   deploy.

9. **The class draw is grindable in principle** — a composed transaction can abandon a registration
   whose drawn class the player dislikes. The class is cosmetic and confers no advantage, so this is
   a fairness-of-presentation question rather than a money one, but it would distort the published
   distribution. *Confirm:* write a LiteSVM case that abandons and retries until a chosen class
   appears.

10. **The entry packet's nonce field may be entirely decorative.** It is decoded and never compared
    against anything on chain; replay protection comes from the entry account's seeds and the
    sixty-second window instead. *Confirm:* grep the program for any read of the nonce after decode.

11. **The published bundle may carry more about a player than intended** — a stable cross-pool device
    marker and per-screen timings are written into a permanent public record. *Confirm:* read one
    published bundle and check which fields identify a returning player.

12. **A stalled vendor response body has no timeout on most paths.** The abort timer is cleared when
    the response head arrives, not when the body completes. One adapter was explicitly fixed after an
    incident and is tested; the others were not. *Confirm:* point one adapter at a server that sends
    headers and then holds the connection open.

### 12.2 Gaps — things that are absent rather than wrong

Absence is invisible to a grep, so it has to be looked for deliberately.

**No test crosses a process boundary.** 121 test files, and every one runs inside a single process
against in-memory doubles. No CI job starts Postgres, so all 15 migrations and all six
Postgres-backed adapters are unexecuted by any automated check. No CI job runs a browser journey.
The one end-to-end harness in the tree is invoked by no workflow and its scripts reference files
that do not exist.

**No reconciliation anywhere.** Five pairs of sources of truth are never compared: the chain against
Postgres; Postgres against the published bundle; the treasury's real balance against the two
book-keeping fields that are supposed to explain it; the committed payout list against what the
chain actually paid; and a vault's balance against its pot. Any one of these, run on a schedule,
would have caught at least one CRITICAL in this report.

**No alerting.** Metrics are counted in memory and written to standard output. Only one of the four
services builds a monitor at all, the Prometheus sink is selected nowhere, the metrics route is
unmounted, and the alert channel has no caller. Nothing pages a human for anything. The closest
thing to monitoring is a fifteen-minute health probe that covers two of the four services and does
not cover the daemon — the one service that is the sole exit from every intermediate on-chain state.

**No runbook for the incidents that can actually happen.** There is no procedure and no script for:
a stuck pool, a leaked settlement key, a daemon outage, restoring the data that has no on-chain
source, or undoing a frontend deploy. The operating manual is good where deployment is concerned and
largely silent where recovery is.

**No second reviewer.** The shipped registry has one member, and the published appeal rule requires
a different reviewer from the one who upheld the flag. Every appeal is therefore undecidable by
construction.

**No request-size limit, and rate limiting off by default.** The hygiene module's three switches all
default off and none is set in any committed deployment file.

### 12.3 Systemic patterns

Five patterns account for most of this report. Naming them is more useful than the individual
findings.

**1. Every seam is tested from one side only.** The producer's test re-applies the producer's own
transform when reading back; the integration harness writes straight to the store the consumer
reads; the read-API tests answer their own SQL from a stub; the on-chain suite builds its own
client. Each of these is a reasonable unit test. Together they mean the one class of defect that
cannot be caught is a producer/consumer contract mismatch — and that is exactly where both of the
worst defects live. *(B-01, A-01, B-05, G-01, G-02)*

**2. A missing value and a failed lookup are the same value.** `null` means "no data" and "the
service is down"; an empty list means "nothing to show" and "the join can never match"; a caught
exception means "not eligible" and "the vendor timed out". Each collapse turns a loud failure into a
quiet wrong answer. *(B-01, C-02, C-04, D-01, D-02)*

**3. A control is documented as wired and is wired to nothing.** The metrics sink, the alert
channel, the rate-limiter sweep, the detection pipeline's hard block, the bundle archive, the
dependency advisory gates, the class-digest package. In each case a module's own header describes a
live mechanism, and no caller exists. The docstring is the only evidence anyone is relying on.
*(A-02 … A-08, E-02)*

**4. A control's scope is narrower than its output claims.** The drift detector prints "every
instruction's wire contract matches" after checking 19 of 32 and none of the money-moving ones. The
integration suite reports every test passed when the artifact it was supposed to drive is absent.
The standing-rules gate reports clean if the file it inspects is missing. The red-main watcher
watches one of the four lanes that run on main. Each of these is worse than no control, because it
produces a confident green. *(A-01, G-03, G-04, E-03)*

**5. Fail-closed is applied at the wrong granularity.** Vendor failures correctly refuse to proceed,
but the refusal is then recorded as a permanent on-chain fact ("sanctions hold") rather than a
retryable condition, and the publish step sits before the payment step so an upload failure strands
a sealed pool. Failing closed is right; making the closure irreversible is not. *(C-01, C-02)*

### 12.4 The one thing

If only one thing can be done before this ships: **write a single test that drives one pool from a
browser-shaped ciphertext write, through the real HTTP handler, into Postgres, out through the
crank, to a paid winner — and run it in CI.** That one test fails today for at least four
independent reasons, each of which is a CRITICAL in this report. Nothing else in this audit would
have been found faster or more cheaply.

## TIER 1 — the four defects that stop the product working

### Commit 1 — `ciphertext: store sealed entries under the pool id the crank reads`

Closes the single defect that makes every pool settle wrongly.

`backend/packet/src/server.ts:205` writes each player's sealed allocation into `sealed_entries`
keyed by `poolKey(b.pool)`, where `b.pool` is the pool's PDA address and `poolKey` (defined at
`server.ts:212-217`) is a polynomial hash producing a 62-bit number. Three consumers read that table
by the pool's on-chain **numeric** id instead: the settlement crank at

### Commit 2 — `ciphertext: prove ownership before accepting a sealed entry`

`backend/packet/src/server.ts:186-207` accepts a sealed allocation for any `(pool, player)` from
anyone. It checks only that both look like base58 addresses and that the body decodes to exactly 175
bytes. There is no signature, no entry packet, no proof the caller controls `player`, no check that
the pool exists or is open, and no check that the player has an on-chain entry. The store's write
(`backend/sealing/src/store.ts:70-78`) is an unconditional upsert. The sibling routes `/attestation`
and `/notify` on the same server both verify a wallet signature.

Consequence: anyone can replace any named entrant's sealed allocation with random bytes, which makes
that entrant score all losses at settlement and hands the attacker the prize pool. It also lets a
player destroy their own paid entry by starting a second run, because the ciphertext write happens
before any duplicate check.

Fix: require an Ed25519 signature by `player` over a canonical message binding the pool, the player
and a hash of the ciphertext. Verify it exactly as `backend/packet/src/attestations.ts:102` already
does for the clickwrap; put the canonical message builder in `backend/_shared/src` beside
`attestation-message.ts` so the browser and the service cannot drift. Separately, refuse the write
when the pool is unknown or no longer open, and refuse to overwrite an existing row for a pool that
has sealed. Update the browser's caller at `app/src/entry/services.ts:72-78` to sign and send it.

Expected files: `backend/_shared/src/` (a new canonical message module and its export),
`backend/packet/src/server.ts`, `app/src/entry/services.ts`, `app/src/entry/submit.ts`,
`backend/packet/test/packet.spec.ts`.

Acceptance: a test posting a well-formed ciphertext for a wallet it does not hold the key for gets

### Commit 4 — `vault: land every drain on zero or on rent exemption`

**This is an on-chain change. Write it and test it; do not deploy it in this session.**

The prize vault is a zero-data, System-owned PDA funded at `open_pool` with exactly `pot_lamports`
(`programs/blotto_cup/src/instructions/open_pool.rs:154-160`), and every exit debits a computed
amount rather than the balance (`programs/blotto_cup/src/vault.rs:60-81`). The design drains it to
exactly zero. The Solana runtime refuses any transaction whose post-state moves a writable account
from rent-exempt to rent-paying, and a zero-data account is rent-exempt only at or above 890,880
lamports. So anyone can send a pool's vault one lamport — the address is derivable from the public
pool id — and the final `pay_prizes` debit, and `trigger_refund`'s pot return, then fail for ever
with an insufficient-funds-for-rent error. The pot is frozen, the entrants are unpaid, and because
`free_tier_slot` is reached only from `pay_prizes` or the two refund paths, that tier can never open
another pool.

`docs/internal-review.md:42-49` records this scenario as considered and accepted, on the reasoning
that nothing in the program reads those balances. That reasoning is correct about the program and
wrong about the runtime.

Fix: make `vault_debit` in `programs/blotto_cup/src/vault.rs` rent-aware. When the post-balance would
be non-zero and below `Rent::get()?.minimum_balance(0)`, sweep the residue into the same transfer so
the account lands at exactly zero. For the batched `pay_prizes` path the sweep must be gated on the
final batch, so pass that in rather than inferring it. Check the platform treasury for the same
shape while you are there: it is also a zero-data System PDA and `refund` debits exactly
`entry_lamports` per entry, so a treasury standing at a small residue above the withdrawal floor has
the same failure mode.

Expected files: `programs/blotto_cup/src/vault.rs`,
`programs/blotto_cup/src/instructions/pay_prizes.rs`,
`programs/blotto_cup/src/instructions/refund.rs`, `tests/litesvm/tests/`,
`programs/blotto_cup/tests/vault_model.rs`.

Acceptance: a LiteSVM case that airdrops 1 lamport to a pool's vault after `open_pool` and then runs
the pool to `Paid`. **First establish whether the harness can see this at all**: add the airdrop to
an existing passing lifecycle case and confirm it goes red. If it stays green, the in-process
validator does not model the rent-state transition and the test must run against a real validator
instead — say so and do not claim the fix is verified by a test that cannot fail.

## TIER 2 — defects that break a journey or lose money on a common failure path

### Commit 5 — `crank: refuse to settle a pool whose entries are incompletely read`

`backend/reveal/src/crank.ts:151-152` reads the Pool account (which carries `entrants`) and then, in
a separate call, reads the Entry accounts by program-account scan. Nothing compares the count. The
only downstream check (`backend/reveal/src/missing.ts:41-43`) asserts gapless indices, which passes
whenever the missing seats are the highest ones — exactly the seats registered last. A lagging RPC
backend therefore settles the pot against an incomplete field, permanently, because
`commit_results` cannot be re-run.

Fix: immediately after the entries read, require `chainEntries.length === pool.entrants` and throw
otherwise. The daemon's sweep already retries a throwing pool on the next tick, so waiting is the
correct behaviour. Assert the same in `recomputeRanking`.

Acceptance: a test where the fake chain returns one fewer entry than `entrants`, and the crank
throws instead of committing.

### Commit 6 — `crank: publish after paying, not before`

`backend/reveal/src/crank.ts:202` awaits the Irys upload before `commitResults` at `:268` and
`payPrizes` at `:293`. A persistent publish failure — an unfunded upload wallet, a gateway outage —
aborts the crank, and a sealed pool cannot be refunded (`trigger_refund` requires state `Open`), so
the pot and the tier are stuck until the upload succeeds. Publication is a verifiability step, not a
payment step.

Fix: move the publish call after `pay_prizes`, and record a publish failure as a non-fatal step so
the pool still reaches `Paid`. Separately, assert the Irys wallet's balance at startup in
`backend/reveal/src/main.ts`, the way `backend/reveal/src/startup.ts:109-126` already asserts the
settlement signer's.

Acceptance: a test where the publisher always throws and the pool still reaches `Paid`.

### Commit 7 — `screening: a vendor that cannot answer must not place a permanent hold`

`backend/reveal/src/winner-screening.ts:102-105` catches every throw from the screening check —
including the error raised when *all* sources failed to answer — and returns a hold. The crank then
lands `place_sanctions_hold` on chain, which is a single boolean: it cannot distinguish "a published
list named this wallet" from "our vendor timed out". `pay_prizes` escrows the whole share, the pool
reaches `Paid`, and the daemon's review clock only considers *flagged* entries
(`backend/reveal/src/daemon.ts:220`), so a held-but-unflagged entry is never revisited. The only exit
is an admin-signed lift that nobody is told is needed.

Fix: treat `screening_unavailable` as retryable — leave the pool short of commit and re-screen on the
next tick — rather than as grounds for an on-chain hold. At minimum, teach the review clock to
re-screen held-but-unflagged entries and drive the lift.

Acceptance: a test where every screening source throws, and the crank does not commit and does not
place a hold, and the pool settles normally on a later tick once screening answers.

### Commit 8 — `indexer: replay events in chain order after a backfill`

`backend/indexer/src/backfill.ts:78-110` walks signatures newest-first and applies the projection
inline per signature. The projection is order-dependent by its own documentation, and the
pool-opened event is a full upsert that resets state, entrant count and paid mask. Ingesting a
pool's history in reverse therefore ends with the pool marked open and empty. This runs on every
first boot against an empty database.

Fix: the cheapest correct change is to have the backfill command call the existing `rederive()` when
it inserted anything — `rederive` already replays in the correct order. Alternatively, buffer the
walk into the ledger only and project afterwards.

Acceptance: a test that ingests one pool's full event history through the backfill path in reverse
and asserts the derived row ends `Paid`, not `Open`.

### Commit 9 — `packet: stop spending a paid vendor lookup on an unauthenticated page view`

`GET /geo` is unauthenticated, and every request from an unseen client address costs one paid
lookup; the cache keys on the address with a short lifetime and never caches a failure. The app
fires it from an effect on every mount of the entry page. The module's own comments record the
budget as roughly 1,000 lookups a day. When the quota is spent the vendor answers 429, which the
adapter deliberately never retries, so every entry is refused — with no alert anywhere.

Fix three things in `backend/packet/src`: put a second source behind the same lookup interface, the
way `backend/sanctions/src/composite.ts` composes sources; raise a monitor event on quota and auth
errors rather than only writing to standard output; and stop spending a lookup on a page view that
has not yet reached the entry flow.

Acceptance: a test that a quota error raises a monitor event, and a test that the composite falls
through to the second source.

### Commit 10 — `app: give the player a way out of a hung sign-in and a missing review service`

Two dead ends, same shape: a failure and an absence render identically as nothing.

`app/src/wallet/privy-bridge.tsx:360-365` pins auth status at "initializing" for exactly as long as
the provider's ready flag is false, and nothing in the app times that out. In that state the header
renders an inert placeholder instead of the sign-in link, the sign-in page greys out every button
with no explanation, and the entry page points at a control that does not exist.

`app/src/app/pools/[pool]/results/appeal.ts:28-44` returns `null` for four different reasons — the

player whose share was forfeited sees no appeal section at all, while the published copy promises a
seven-day appeal window.

Fix: arm a timer in `app/src/wallet/auth-provider.tsx` and fall through to the honest rejected state
that already exists with copy; render the sign-in link rather than a placeholder once it passes.
Make the appeal fetch return a discriminated result and render an honest "could not reach the review
service, your window is still open" state whenever the viewer is in the forfeited list.

Acceptance: two tests, one per dead end, asserting a reachable control exists in the failure state.
