# T1 — every wallet's allocation, and the chain's record of it

**Refund, sparse — a pool below the minimum field returns every entry in full**

Each wallet sets seven allocations of five stats, each summing to exactly 100, in the fixed order Strength · Speed · Heart · Wit · Durability.

The allocations below are **derived from the seeds frozen in `T1.plan.json`** (PR 132, merged 2026-09-16T00:07:24Z, plan sha256 `215cb73cb137…6cb8`). This file adds no prediction — it renders one that was already fixed, so it reads the same whenever it is generated.

## How to read the state column

| State | Meaning |
|---|---|
| `PENDING` | no entry has landed yet; the intended allocation only |
| `COMMITTED` | the entry landed and the chain holds `sha256(battles ‖ salt)`, which nobody can open yet |
| | **For this pool `COMMITTED` is terminal.** It refunded, and a refunded pool never reveals its secret on this tree — so these hashes stay sealed and no seat here can reach `VERIFIED`. The finding, with its evidence, is docs/testing/TESTING-REPORT.md. |
| `VERIFIED` | the pool revealed its secret; the published battles and salt recompute to the hash the chain recorded at entry |

A salt is never printed before its pool reveals: publishing one early would let a guess at that entry's allocation be confirmed, which is the sealing property gone.
