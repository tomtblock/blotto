# Blotto Cup — the mobile channel and the Solana dApp Store

**Who this is for.** Whoever builds, tests, ships or maintains the Android package, and anyone
changing the app who needs to know what a change means for the phone. It assumes
[`HOSTING.md`](HOSTING.md) (where the site runs) and [`OPERATING-MANUAL.md`](OPERATING-MANUAL.md)
(running a deployment). This document is canonical for **everything that differs on mobile, the
Android package, and the store submission**. Decision `D-E18` in
[`../architecture/DECISIONS.md`](../architecture/DECISIONS.md) is the ruling it implements.

**Current reality (2026-09-30).** Nothing has been submitted to the Solana dApp Store, and nothing
will be before the mainnet launch ([`../ROADMAP.md`](../ROADMAP.md) §3). The Android package has
been generated, signed with the store key, patched (§3), installed on an Android 15 emulator and
taken through sign-in, verification and a devnet entry (§5). The generated project is committed
under `mobile/blotto-cup/` with both patches applied and the diagnostic switches off. The app-side
changes are live on every deploy and change nothing for a desktop or iOS visitor (§1). The short
way in for anyone new is [`mobile/README.md`](../../mobile/README.md).

## 1. One app, every channel

There is **one build of Blotto Cup**. The Android package is a WebView shell, generated by Solana
Mobile's own `webshell` tool, that opens the deployed site. It carries the app's name, icon and
address and nothing else: no page, no rule, no number, no copy of the scoring engine. So:

- **Every deploy reaches the site and the phone at the same moment.** Merging to `main` ships to
  both. The package is rebuilt only when its own three facts change (§6).
- **Two players in one pool are on one build.** What decides a result is the on-chain program and
  the scoring engine (`backend/scoring`), which no channel touches; what builds the entry on the
  device is the same bundle on every channel. The one way to be on a different build — a page
  left open across a deploy — is closed by the build check (§2, item 5).
- **The channel is cosmetic to the competition**, in the same sense the pass class is. Nothing on
  the money path, the board, sealing, scoring or ranking reads it (`app/src/channel/channel.ts`
  says so at the top, and the list in §2 is the whole of what does).

The alternatives were rejected on record: a fork (two copies of audited money code, drifting), and
a separate repository for the shell (one feature across two repositories, and listing copy outside
the language gate). D-E18.

## 2. What differs on mobile — the complete list

Every difference between the site in a desktop browser and the same site on a phone. **If a
change adds to this list, it changes this section in the same commit** (the rule
[`../README.md`](../README.md) sets for every document).

The channel is read from the browser's user agent by `app/src/channel/channel.ts`: `web` (the
default, including iOS), `android-browser` (Chrome and other browsers on Android), or `webshell`
(inside the Solana Mobile shell, which appends the token `Solana Mobile Web Shell`). It is `web` on
the server and during hydration, so every page's first paint is the web page.

| # | On which channel | What differs | Why | Where |
|---|---|---|---|---|
| 1 | Android (browser and shell) | The **mobile wallet standard** is registered as a wallet-standard wallet named "Mobile Wallet Adapter". It appears in the sign-in list beside any extension the browser has, and connects to whichever MWA wallet app is installed (Phantom, Solflare, the Seeker's Seed Vault Wallet) through an Android intent | A phone has no browser extension; without this the sign-in page would list nothing | `app/src/wallet/mobile-wallet.tsx`; the library (`@solana-mobile/wallet-standard-mobile`) is downloaded only on Android |
| 2 | Shell only | The **Google and X sign-in buttons and the "More wallets" door are not drawn**; the page opens on the wallet rows with a sentence that says so | Google refuses to open its sign-in page inside an embedded WebView (`disallowed_useragent`); the provider's own modal is a browser surface | `app/src/app/signin/signin-client.tsx`; `COPY.signin.webshellSubtitle` |
| 3 | Any (in practice, a mobile wallet) | A wallet that signs in but **offers sign-and-send only** is told, in words, that it cannot enter a pool, and which wallets can | The entry path has the wallet sign and hands the transaction back, then adds the pass asset's own signature after it — a founder-ruled order (`app/src/tx/execute.ts`). A wallet without `solana:signTransaction` cannot take part in that; reversing the order for it would reintroduce the risk the ruling removed | `app/src/wallet/types.ts` (`signerLimit`); `direct-session.tsx`; `play-client.tsx`; `COPY.gate.signerCannotSignTransactions` |
| 4 | All | The response headers' `connect-src` allows `ws://localhost:*` and `ws://127.0.0.1:*` — the phone's **own loopback**, nothing remote | The mobile wallet standard's browser transport is a plain WebSocket to the wallet app on the same device | `app/next.config.ts`; pinned by `app/src/chain/headers.test.ts`, which also refuses any other plain-`ws` origin |
| 5 | All | **The build check.** The play page asks `/api/version` which build is live — once when it opens, and again just before the seal — and a page from an older build stops before anything is signed, with a reload | A phone app left in the background across a deploy would otherwise seal an entry from an older bundle; two players in one pool must be on one build | `app/src/build/version.ts`; `app/src/app/api/version/route.ts`; `next.config.ts` (`NEXT_PUBLIC_BUILD_VERSION`); `COPY.build` |
| 6 | All | A **web app manifest** at `/manifest.webmanifest` and an icon at `/icon.png` | Browsers use it for "add to home screen"; `webshell init --manifest` reads it to seed the package's name, icon and start URL, so the shell and the site cannot drift on those | `app/src/app/manifest.ts`; `app/public/icon.png` |
| 7 | Android (browser and shell) | **Sign-in is one wallet request.** The direct route signs in through the wallet's own sign-in (`solana:signIn`: connect and the signed statement together, one-line statement) instead of connect and then a separate signature. A wallet that offers no sign-in, or answers it with no result, takes the two-step route as on the web | A wallet app is reached one session per request, and two sessions in a row race inside the shell: the WebView fires the second intent while the wallet's screen is still closing, and the wallet revokes the token it just granted (found 2026-09-30 on an emulator; §9 has the log) | `app/src/wallet/direct-sign-in.ts` (`walletSignIn`); `direct-session.tsx` |
| 8 | Android (browser and shell) | **No wallet prompt launches while the page is not in front.** Before every prompt — the seal signs a message and then, a few RPC round trips later, the entry transaction — the page waits until it is visible and focused, plus 300 ms for the wallet's screen to finish closing; 2.5 s at most, then it goes anyway | The same race, for the two signatures the seal takes in a row | `app/src/wallet/in-front.ts`; `direct-sign-in.ts` (`settle`) |
| 9 | All (read by the shell's wallet) | **The site publishes the package's identity** at `/.well-known/assetlinks.json` — the package id and the signing certificate's SHA-256 — and the gate lets that path through without a cookie. The shell, for its part, launches the wallet with `startActivityForResult` (§3's patch) so the wallet can read which app is asking | A mobile wallet verifies WHO is asking before it re-authorizes without a prompt: it reads the calling package and checks it against that file on the identity URI's host (Solana Mobile's `digital-asset-links-android`, used by MWA wallets). Unverified, Phantom allows the first connect — the player approves it on screen — and refuses every silent re-authorization after it, so no signature ever completes (found 2026-09-30; §9). A browser is exempt: the wallet trusts the page's origin | `app/src/channel/android-app.ts`; `app/src/app/.well-known/assetlinks.json/route.ts`; `app/src/proxy.ts`; `mobile/patch-shell.sh` |
| 10 | Any browser without Ed25519 in WebCrypto — in practice an older Android WebView | **Ed25519 is polyfilled where `crypto.subtle` lacks it**, before the entry's pass-asset keypair is generated: a probe first, Solana's own polyfill downloaded and installed only on failure. A modern browser pays nothing | The entry transaction is partial-signed by a keypair made on the device with WebCrypto Ed25519, which Chrome shipped by default only in 137; the emulator's WebView was Chromium 124, and kit's guard threw after the ciphertext was stored and before the wallet was asked (§9). The dApp Store package is a WebView | `app/src/chain/ed25519.ts`; `app/src/entry/services.ts`; `@solana/webcrypto-ed25519-polyfill` |

Two consequences that are not code changes:

- **The device marker becomes per app.** The marker (`app/src/entry/device.ts`) is a random secret
  in the browser's storage; the shell's WebView has its own storage, separate from Chrome's. One
  person using both has two markers. Detection's device-correlation signal is best-effort by design
  and treats this as absence, not as a fake ([`../compliance/DATA-INVENTORY.md`](../compliance/DATA-INVENTORY.md)).
- **The mobile wallet library keeps its authorisation token** in one storage key of its own
  (`SolanaMobileWalletAdapterDefaultAuthorizationCache`), so a second sign-in does not re-prompt
  the wallet app. Listed in the data inventory.

## 3. Building the Android package

Done on a workstation, by hand, at the moments §6 names. Nothing here runs in CI (§7).

**Prerequisites** (once): Node.js **24 or newer** (the `webshell` command requires it; the rest of
the repository runs on 20 — use a version manager), a JDK (Android Studio's bundled one serves:
`export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"` on macOS, and its
`bin` on the `PATH`; without it the build stops at "Unable to locate a Java Runtime"), Android
Studio with the Android SDK and command-line tools, and `apksigner` on the `PATH` (it ships with
the SDK's build-tools).

**The commands.** Run on macOS on 2026-09-30 with the `solana-mobile` npm package (0.5.0); the tool
is new and its flags may move, so run `--help` first and read what it says.

```bash
# 1. From the repository root. The generated project lives beside this file.
cd mobile

# 2. Generate the Android project. One line; read the prompts — the package id is the
#    permanent identity of the listing (§8) and is set ONCE. The `--manifest` form
#    (seeding the name and icon from /manifest.webmanifest) did NOT work against our
#    host on 2026-09-30: the apex host redirects to www and the tool read the redirect
#    page as the manifest ("Unexpected token '<'"). Name the site and the app instead.
npx solana-mobile@latest webshell init blotto-cup --url https://<the deployed host> --app-name "Blotto Cup" --application-id gg.blotto.app --keystore-path <path outside the repository>/blotto-dappstore.jks --keystore-alias blotto

# 3. Apply the two patches the generated project needs before a wallet app works with
#    it; `webshell init` (0.5.0) writes neither (§9 has both findings). One: the
#    Android 11+ `<queries>` block, without which the shell cannot open the wallet at
#    all ("Failed to connect to the wallet websocket"). Two: the wallet launched with
#    startActivityForResult, without which the wallet cannot see which app is asking,
#    cannot verify it, and refuses every re-authorization. Idempotent; run after every init.
./patch-shell.sh

# 4. Build the signed release package. The two passwords come from the environment
#    (mobile/webshell.env.example names them), never from a file in the tree; when a
#    variable is unset the tool prompts for it.
SOLANA_MOBILE_KEYSTORE_PASSWORD='…' SOLANA_MOBILE_KEY_PASSWORD='…' npx solana-mobile@latest webshell build blotto-cup --keystore-path <the same path> --keystore-alias blotto

# 5. Confirm it is signed with the store key (the certificate fingerprint must match
#    the one recorded in the operator's password manager, §4).
apksigner verify --print-certs blotto-cup/app/build/outputs/apk/release/app-release.apk

# 6. Publish that certificate's fingerprint — the "SHA-256 digest" line of step 5 — in
#    `app/src/channel/android-app.ts` (ANDROID_SIGNING_CERT_SHA256), and deploy. The
#    site then serves /.well-known/assetlinks.json naming the package and its
#    certificate, which is how a wallet verifies the app (§2 item 9). Not a secret: both
#    are readable from the published package. A new signing key means a new entry; the
#    old one stays listed while packages signed with it are still installed anywhere.
```

The tool sets the WebView's user agent to carry the token `Solana Mobile Web Shell` (its
`MainActivity.kt`), which is what `app/src/channel/channel.ts` reads.

`webshell init` writes `twa-manifest.json` (its own settings, re-read on a later `init`) and
`gradle.properties` (with `SOLANA_MOBILE_VERSION_CODE` and `SOLANA_MOBILE_VERSION_NAME`).

**Commit the generated project** under `mobile/blotto-cup/`, so the build is reproducible from the
repository and the patches travel with it. `mobile/.gitignore` refuses the keystore, the passwords,
the build output and the machine-local files; check the list before the first commit:

```bash
# From the repository root. First, if the project carries the diagnostic switches (§5), revert them:
sed -i '' 's/setWebContentsDebuggingEnabled(true)/setWebContentsDebuggingEnabled(BuildConfig.DEBUG)/; s/isDebug = true,/isDebug = BuildConfig.DEBUG,/' mobile/blotto-cup/app/src/main/java/gg/blotto/app/MainActivity.kt
git add mobile/blotto-cup
git status --short mobile/        # no .jks, no build/, no local.properties — .gitignore refuses them
git diff --cached --stat | tail -1
```

**Who builds, who installs.** The key holder builds; everyone else installs the built `.apk`. A
package signed with any other key installs and opens, and signs in, but no signature after that
completes: the wallet verifies the package's certificate against the one fingerprint the site
publishes (§2 item 9), and a second "development" fingerprint cannot be published without letting
anyone with that key present as Blotto Cup on a wallet's consent screen. Share the `.apk` — it is
what the store will publish — as an attachment on a GitHub release of the repository, marked
pre-release while it opens devnet, named with the `versionCode` and the commit it was built from.
Never share the `.jks`.

**Which host.** For a hackathon or a test, a devnet preview deployment's host. For the store, the
production host after the mainnet launch. The host is baked into the package, so the two are
different packages with different `versionCode`s; never submit one built against a preview.

**The name `gg.blotto.app` is a proposal** (the package id is owner-reserved and permanent once
published). Change it before the first `init`, never after.

## 4. The signing key

The store refuses an update signed with a different key from the first release, so **losing the
key means the listing can never be updated**, and **leaking it means anyone can publish as us**.
It is handled under [`../../CONTRIBUTING.md`](../../CONTRIBUTING.md#keys-and-secrets) like every
other key.

- **A key for the dApp Store only.** Solana Mobile refuses a package signed with a Google Play
  signing key. If the app is ever listed on Play, that is a second key.
- **Create it once**, outside the repository, with the operator's password manager open:
  `keytool -genkeypair -v -keystore blotto-dappstore.jks -alias blotto -keyalg RSA -keysize 2048 -validity 10000`.
  (`webshell init` can create one for you; the explicit command puts you in charge of where it
  lives.)
- **Record**: the keystore file (as an attachment), both passwords, the alias, and the certificate
  SHA-256 fingerprint from `apksigner verify --print-certs`. A second copy of the file in a second
  place the operator controls.
- **Never**: commit it, paste it into a chat, a ticket or a CI secret, or sign anything but this
  package with it. `mobile/.gitignore` refuses `*.jks`, `*.keystore` and `*.p12`; the pre-commit hook
  and the gitleaks lane do not know this shape, so the ignore line and the operator's care are the
  controls.

## 5. Testing on an emulator or a phone

**The emulator.** Android Studio → *Device Manager* → *Create device* → a Pixel with a system
image that includes **Google Play** (API 34 or 35), so the Play Store can install a wallet.
Start it, sign into Play, install **Phantom** (or Solflare). In Phantom: *Settings → Developer
settings → Testnet mode → Solana devnet*, then fund the address from the devnet faucet (the site's
own "Get test SOL" link on the balance screen when `NEXT_PUBLIC_DEVNET_FAUCET=1`, or
`solana airdrop`).

**The site in the emulator's Chrome** (no package needed): open the deployed host. Sign in: the
list shows "Mobile Wallet Adapter"; tapping it opens Phantom, which asks once to connect and sign
the statement (item 7). Chrome first asks for **local network access** — the wallet answers over
the phone's own loopback — and the sign-in fails until that is granted; the shell needs no such
grant, it launches the wallet as an app. Enter a pool: Phantom shows the attestation signature,
then the seal's signature and the entry transaction. This exercises items 1, 3, 4, 5, 7 and 8 of §2.

**A package someone else built** (the usual case — §3 "Who builds, who installs"): download the
`.apk` from the release, `adb install -r app-release.apk`, and continue below. It must be the
key holder's build; a package signed with another key stops at the first signature after sign-in.

**The package**: `npx solana-mobile@latest device install blotto-cup/app/build/outputs/apk/release/app-release.apk`
(or `adb install -r …`), then open "Blotto Cup" from the app drawer. The sign-in page opens on the
wallet rows (item 2). Everything else is the site. To watch the wallet handshake:
`adb logcat -c && adb logcat | grep -i "solana-wallet\|PhantomMWA\|AuthRecord"` — one
`v1/associate/local` line per wallet request, and "Authorize request completed successfully" with
`cluster='devnet'` on the sign-in.

**Verified 2026-09-30** (emulator: Pixel, Android 15 / API 35 with Google Play; Phantom on Solana
devnet; the site at `www.blotto.gg`), in order, each from Phantom's own log:

- the playground's capability check — Phantom signs a transaction, the entry path's requirement;
- sign-in and a devnet pool entry in Chrome (after the local-network grant);
- the package built, signed and installed, opening on the wallet rows (item 2);
- **inside the shell, with §3's two patches and item 9's file live:** the `solana-wallet://` launch;
  sign-in as one session (item 7: one `associate/local`, `Authorize request completed
  successfully`, `cluster='devnet'`); the verifier passing — `MWA session started … callingPackage=
  gg.blotto.app` and `IdentityVerifier: DAL verification for https://www.blotto.gg (caller=
  gg.blotto.app): true`; then three silent re-authorizations (`AuthRecord still valid; reissuing`)
  each followed by a signature — the age attestation and the seal's ciphertext message, twice. No
  "Revoking AuthRecord". That is the whole wallet integration the store needs.

**And the entry itself, 04:22 UTC:** after §2 item 10 deployed, the same shell (no rebuild — the
site carries the fix) sealed an easy-mode entry into devnet pool #50 and the play page showed
"I'm in. Seat 1 of 64". The first two attempts had stopped after the ciphertext with "The network
request did not go through" — the WebView's Network tab showed every request green, and the cause
was the WebView's missing Ed25519 (§9). That closes the loop the store needs: everything a player
does, from the app drawer to a seat.

**Reading the WebView's network from the Mac** (diagnostic build only — revert before any store
build): in the generated `MainActivity.kt` change `setWebContentsDebuggingEnabled(BuildConfig.DEBUG)`
to `(true)` and `isDebug = BuildConfig.DEBUG` to `true`, rebuild, reinstall; Chrome on the Mac →
`chrome://inspect#devices` → *inspect* the Blotto Cup WebView → Network. The console then reaches
`adb logcat` too. A release build forwards neither.

**One emulator at a time**, and nothing else heavy on the machine: two emulators with Phantom and
the shell open froze it twice, and after four hours the board art rendered as noise and requests
stopped completing. The clips (§9) are most of the load; a cold boot restores it for a while.

**A real phone**: enable developer options and USB debugging, plug it in, and use the same
`device install`. A Seeker answers the open question in §9 about its built-in wallet.

**What to record for a demo:** Android Studio's screen recorder, or
`adb shell screenrecord /sdcard/blotto.mp4`. The strongest moment is the verify page recomputing a
settled pool on the phone.

**Automated coverage** ([`../testing/TESTING-REPORT.md`](../testing/TESTING-REPORT.md) §8 lists
what is not covered): `app/src/channel/channel.test.ts` pins the channel detection against the
installed library's own token; `app/src/app/signin/signin-channel.test.tsx` renders the sign-in
surface per channel and asserts the web surface is unchanged; `app/src/build/version.test.ts` the
build check's verdicts; `app/src/chain/headers.test.ts` the loopback-only widening. No CI lane
opens an Android emulator; a real MWA wallet is exercised only by hand.

## 6. Change control: what a change means for the phone

**The rule: a change to the app is a change to both channels, and needs nothing from `mobile/`.**
The package is rebuilt and resubmitted only when one of its own three facts changes.

| You are changing | On the phone | What to do |
|---|---|---|
| Any page, copy, board, rule, style, dependency of `app/` | Live on the next deploy, like the site | Nothing extra. Check it at 375 px (the `journey` lane already does) and, for anything on the sign-in or entry path, in the emulator (§5) |
| The sign-in page (`app/src/app/signin/`), the wallet seam (`app/src/wallet/`), the tx seam (`app/src/tx/`) or the response headers (`next.config.ts`) | Live on the next deploy — and these are the files the channel logic lives in | Read §2 first. Run the emulator path (§5) before merging. If the change adds a channel difference, add it to §2's table in the same commit |
| The **app name, icon or start URL** (`app/src/app/manifest.ts`, `app/public/icon.png`) | The site changes at once; the package shows the OLD name and icon until rebuilt | Rebuild the package (§3, step 2 re-reads the manifest) with a higher `versionCode`; submit it as an update (§8) |
| The **deployed host** (a domain move) | The package keeps opening the old address | Rebuild with the new `--url` (§3), and publish the identity file on the new host too — the wallet checks the host the app names; submit as an update. Keep the old host answering until the review is through |
| The **package id** or the **signing key** | Never | Either one breaks the listing's identity. The store treats a new package id as a new app and refuses a new key outright (§4) |
| `mobile/**` only (the generated project, this manual's commands) | Nothing until a package is built from it | `ci-fast` still runs in full on the commit (§7); the language gate reads every file here |
| The program, the backend, `config/` | Exactly as for the site; the phone is a client of the same services | Nothing extra |

**A change in one commit.** A change that touches the channel logic (§2's "Where" column) says so
in its commit body, the way [`../../CONTRIBUTING.md`](../../CONTRIBUTING.md) ("Commits, branches")
asks for money paths and published claims: it is a client-side surface a phone user cannot see
past, and a reviewer should know to look at it on a phone.

**Version numbers.** `versionCode` is an integer that only rises; `versionName` is what the store
shows. Bump both in `mobile/blotto-cup/gradle.properties` before every rebuild that will be
submitted, and record the pair in the submission's "What's new".

## 7. CI

Nothing in `mobile/` is built or installed by CI, and no lane opens an Android emulator.

What CI does cover: every app-side change in §2 runs through `ci-fast` like any other — the
`node` job (lint, typecheck, the unit suite including the four test files named in §5, the
production build), the `journey` job at 375 px and 1280 px, and the `standing-rules` lane, whose
language gate and dead-files gate read `mobile/` and the new modules like everything else.
`ci-fast` has no path filter, so a commit that only touches `mobile/` still runs it in full — that
is deliberate: the listing copy committed under `mobile/` is public copy and must pass the gate.
`app-test-signer` runs on `app/**` and is unaffected.

**Not automated, on purpose, for now:** building the package in a workflow would need the
signing key as a CI secret, which §4 forbids until there is a reason strong enough to write the
key-handling rules for it. The package is built by hand, a few times a year, by the person who
holds the key.

## 8. Submitting to the Solana dApp Store

Not before mainnet. Everything below is prepared so the submission is a checklist on the day. Read
Solana Mobile's own pages first — they move: the publishing overview, "Submit a new app", "Submit an
update", the listing-page guidelines, the publisher policy (updated 21 July 2026) and the developer
agreement, all under `docs.solanamobile.com/dapp-store/`.

**Before the day — owner decisions and legal (none of these is engineering):**

- [ ] **Listability.** The publisher policy has no clause on paid-entry tournaments with prizes;
      it requires that a listed app follow applicable law and, for financial services a law governs, carry the
      documentation the law requires. No clause is not approval. Ask the dApp Store team in writing
      whether a paid-entry, geo-restricted, 18+ tournament with a fixed prize is listable, with
      [`../compliance/SAFEGUARDS.md`](../compliance/SAFEGUARDS.md) as the supporting document.
      Legal review of the listing is part of the mainnet legal review ([`../ROADMAP.md`](../ROADMAP.md) §3).
- [ ] **The listing copy**, in the founder's voice, passing `./scripts/check-language.sh`. The store
      asks for a name, a short description (**30 characters**), a long description, and a "What's
      new" per release. The store's own category labels are not ours to rewrite — choose the
      category, write the description ourselves.
- [ ] **The icon** (512 × 512). `app/public/icon.png` is the mascot on the brand ground, generated
      as a stand-in; replace it with the founder's art before submission (it is also the manifest
      icon and the wallet consent screen's icon, so replacing the file updates all three).
- [ ] **Screenshots or videos**: at least four, 1080 px minimum, all the same orientation and
      aspect ratio; video in `.mp4`, 1080p recommended. Screens to show: the pool card, the board,
      the sealed confirmation, the results page, the verify page.
- [ ] **The package id** (§3) and the **signing key** (§4), both final.
- [ ] **A publisher account** at `publish.solanamobile.com` (it runs identity checks on the
      publisher), a **publisher wallet** on **mainnet** holding about 0.2 SOL for the publisher, app
      and release records (each is minted on chain; the same wallet is needed for every later
      submission), and a storage provider chosen in the portal (ArDrive is the recommended one).
- [ ] **Reviewer access.** Reviewers may sit in a blocked territory. Prepare a note for the
      submission form saying what the territory gate does and how to reach a reviewable state, and
      whether a test wallet with entry funds is provided.

**On the day:**

1. Build the package against the **production** host (§3), bump the version pair, verify the
   signature (§4), and install it on a phone from the built file to confirm it opens the production
   site and signs in.
2. Portal → *Add a dApp* → *New dApp*: name, descriptions, icon, screenshots, category, the
   reviewer note. Details can be edited before submission.
3. From the app's *Home* → *New Version*: upload `app-release.apk`, write "What's new", approve the
   wallet prompts for the asset uploads and the on-chain records.
4. It enters the review queue. Answers come by email from the publisher-support address within
   three to five business days; an approved release goes live at once.

**Updates** (a rebuilt package, §6): *Home → New Version*, a higher `versionCode` and
`versionName`, the same key, "What's new". Details-only changes can be submitted against the
existing package. The portal-backed CLI (`@solana-mobile/dapp-store-cli`, authenticated with an
API key from the portal's settings) can submit a version from a workstation; it is optional and
not set up.

## 9. Known limitations and open questions

- **Only the key holder's package is verified** (§3 "Who builds, who installs"). Testers install
  the shared `.apk`; a package built with another key demonstrates the pre-fix failure exactly
  ("This wallet cannot sign the confirmation"). This is the wallet standard working as designed,
  not a defect to engineer around.
- **`patch-shell.sh` is pinned to the 0.5.0 template's exact lines** and exits non-zero on
  anything else. A newer `solana-mobile` may change the template; when it does, read what the
  script refuses, patch by hand, and update the script in the same change.
- **Node 24 for the shell tool, Node 20 for everything else.** A version manager (`nvm use 24`
  in `mobile/`, `nvm use 20` elsewhere) is the practical answer; nothing in CI touches the shell.
- **The play page's catch-all error copy** ("The network request did not go through") covers every
  unclassified exception in the entry build, not only network ones — it sent the 2026-09-30
  investigation down a network path first. Worth a distinct sentence for "something in this
  browser could not build the entry"; user-facing copy, so the owner's call.
- **The Seeker's built-in wallet (Seed Vault Wallet)**: whether it advertises `sign_transactions`
  and whether it supports devnet are unverified. If it offers sign-and-send only, a Seeker owner
  can sign in but not enter until §2 item 3's ruling is revisited — which means a change to the
  signing order in `app/src/tx/execute.ts` and a founder decision, not a mobile change. Settle it
  on a Seeker before the store submission.
- **`webshell init` (solana-mobile 0.5.0) generates a shell no wallet can work with**, for two
  reasons, both patched by §3's `patch-shell.sh`; keep running it until the tool changes. Worth
  reporting to Solana Mobile — the owner's call, as it is a public report in the product's name.
  - **No `<queries>` block**, so the package cannot launch a wallet app on Android 11 or newer:
    the intent is silently refused and the page reports "Failed to connect to the wallet
    websocket at ws://localhost:…/solana-wallet" with the wallet installed and working in Chrome
    (a browser is exempt from the rule).
  - **The wallet is launched with plain `startActivity`** (`WebShellViewClient.kt`), so the wallet
    cannot read which app is asking (`getCallingPackage()` needs `startActivityForResult`) and
    cannot verify it against the site's `/.well-known/assetlinks.json`. Phantom's log, on the age
    confirmation after a sign-in that had worked: `callingPackage=null` … `not verified
    (mwaIdentity…)` … `code=-1, message=authorization request failed` … `Revoking AuthRecord`;
    the app shows "This wallet cannot sign the confirmation". A first connect is allowed
    unverified because the player approves it on screen; a silent re-authorization — which every
    signature starts with — is refused. §2 item 9 is the answer: the patch, and the site
    publishing the package's identity. Phantom reads that file with Solana Mobile's own verifier,
    which follows no redirect and requires content type exactly `application/json` — which is
    why the gate exempts `/.well-known/` and the route sets the header by hand.
- **The WebView can be older than the phone's Chrome, and lack Ed25519 in WebCrypto.** With the
  wallet fully working (§5), the entry stopped after the ciphertext was stored and before any
  `signTransaction` session, showing "The network request did not go through" — while the
  WebView's Network tab (read as §5 describes) showed every request green: `packet` 200,
  `ciphertexts` 204, the RPC calls 200. The sentence is the play page's catch-all for an
  exception in the build, and the exception is kit's `ED25519_ALGORITHM_UNIMPLEMENTED` (3610002)
  from `generateKeyPair` — the emulator's WebView is Chromium **124** (`chrome://inspect` shows
  the version), and Chrome shipped Ed25519 in `crypto.subtle` by default in 137. §2 item 10 is the
  answer. A real phone updates its WebView through Play and is usually current; the emulator
  image's is frozen, which makes it the better test.
- **Two wallet sessions in a row race inside the shell** (2026-09-30, Android 15 emulator,
  Phantom). The log of the sign-in as it was — connect, then a separate signature:

  ```text
  02:35:50.256  eth_requestAccounts: user approved
  02:35:50.463  Authorize request completed successfully … cluster='devnet'
  02:35:50.489  PhantomMWA: Clearing scenario                ← session 1 tearing down
  02:35:50.510  START … solana-wallet:/ … result code=3      ← session 2, 47 ms later, delivered to
                                                               the wallet activity still on top
  02:35:51.109  Revoking AuthRecord{id=2 …}                   ← the wallet revokes session 2's token
  02:35:51.631  PhantomMWA: Clearing scenario  ×2
  ```

  Chrome does not fire an external intent from a page that is not in front, so there the second
  session waits for the wallet to close; the shell's WebView fires it at once. Items 7 and 8 of §2
  are the answer: one session for the sign-in, and no prompt while the page is not in front. If the
  log still shows a revoke after them, the next thing to look at is the shell's own intent
  handling (`MainActivity.kt`, `shouldOverrideUrlLoading`).
- **The board is not kept across the build-check reload** (§2, item 5). The pre-flight check
  catches the ordinary case before a board exists; the seal-time case loses the board. Keeping it
  would mean storing allocations on the device, which the data inventory currently rules out.
- **The Privy embedded wallet inside the WebView** is untested and not offered there (§2, item 2).
- **Data on mobile networks**: `app/public/motion` is about 133 MB of clips, cached for a day. The
  package itself stays small (it holds no media), but a first launch on mobile data is heavy.
- **No CI lane exercises a real MWA wallet.** See §5 and §7.
